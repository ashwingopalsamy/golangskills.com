## Scenario 1 — replay-safe payment consumer

### Prompt

A Go Kafka consumer processes `payment.authorized` events. For each event it inserts a ledger row in PostgreSQL, calls a remote rewards HTTP API, then commits the Kafka offset. Production shows duplicate ledger rows and duplicate rewards after crashes. The product owner asks for exactly-once processing and suggests committing the offset before either effect. Design the correct failure semantics, transaction boundaries, idempotency mechanism, acknowledgment point, and recovery behavior. State what cannot be made atomic and what identifiers/constraints must be durable.

### Rubric

Reject offset-first; stable logical event identity; durable inbox constraint; business-level ledger uniqueness; durable pending rewards operation/outbox; remote idempotency or reconciliation; explicit non-atomic boundary; crash-boundary matrix; partition offset ordering; fingerprint mismatch or retention horizon.

### Baseline output, normalized — 9/10

“Exactly once” should mean each logical authorization produces one ledger entry and one rewards operation, despite at-least-once Kafka delivery. Committing the offset first gives at-most-once processing and can permanently lose both effects after a crash.

For each event:

1. Require a stable producer-assigned `event_id` or `authorization_id`. Kafka offset alone cannot deduplicate producer retries that appear at new offsets.
2. In one PostgreSQL transaction, insert an inbox/processed-event record with a unique constraint on `event_id`, insert the ledger entry under a business uniqueness constraint such as `(authorization_id, entry_type)`, and insert a rewards-outbox row whose command ID and idempotency key are deterministically derived from the event.
3. Only after that transaction commits, commit the Kafka offset. A crash before offset commit causes replay; the constraints make it a no-op.
4. Independently dispatch the outbox command to rewards, retrying with the same idempotency key and recording completion only after a definitive response.

The rewards service must durably enforce idempotency-key uniqueness, return the original result for retries, and reject reuse with a different payload. Kafka offsets, PostgreSQL, and HTTP cannot be one atomic commit. Without remote durable idempotency or lookup, exactly-once rewards are impossible. Recovery uses Kafka replay and outbox retries; poison events need quarantine and offset advancement must respect partition ordering.

Missing criterion: crash handling was summarized rather than enumerated at every durable boundary, including explicit offset-commit failure.

### Skill-assisted output, normalized — 10/10

Reject committing the offset first: that changes the contract to at-most-once and loses events before either effect.

Require stable `event_id`, `payment_authorization_id`, a semantic payload fingerprint/schema version, and a stable rewards idempotency key. In one PostgreSQL transaction, claim `event_id` under a unique inbox constraint, alert on fingerprint mismatch, insert the ledger under `(payment_authorization_id, entry_type)`, insert a unique pending rewards operation, and commit. Do not hold the database transaction during HTTP. Call rewards with the persisted key, then persist the result and mark the operation complete in a second transaction.

Commit Kafka offset only after completion and only as a contiguous completed watermark per partition. The response enumerated crashes before the first commit, after the first commit, after ambiguous rewards success, after completion but before offset commit, and during offset commit. Permanent rejection becomes a terminal outcome or an explicit compensating ledger transition.

PostgreSQL, Kafka, and HTTP cannot share an atomic transaction. Exactly-once is logical and contingent on remote durable idempotency or reconciliation. Dedupe and idempotency records must outlive the maximum broker, incident, and manual-replay window.

## Scenario 2 — bounded concurrent image processing

### Prompt

A Go HTTP handler processes up to 100,000 image IDs. The current implementation starts one goroutine per ID; each goroutine acquires an 8-slot semaphore after it starts, calls a downstream API, and sends its error on an unbuffered results channel. The handler returns on the first error. Under cancellation, goroutine count and memory spike, and some requests never terminate. Design the execution lifecycle so downstream concurrency is at most 8, admission is bounded before work starts, the first failure cancels sibling work, no sender can remain blocked after return, and the owner waits for all started work. Explain channel ownership, every blocking point, and the overload choice.

### Rubric

Fixed worker count; pre-work bounded admission; sibling cancellation; no abandoned result sender; single closer and owner wait; cancellation-aware blocking; complete blocking-point analysis; finite downstream timeouts; per-request versus service-wide capacity; explicit overload behavior.

### Baseline output, normalized — 10/10

Use a fixed worker pool; do not create a goroutine per ID. Start at most eight `errgroup` workers and use an unbuffered jobs channel. Workers select between cancellation and job receipt, check cancellation after receipt, call downstream with the group context, and return errors through the group rather than a result channel. The handler cancellation-aware sends each job, closes the channel, and calls `Wait` before returning.

The handler is the only sender and closer. An unbuffered send is the admission boundary, so only an idle worker admits a job. Job send and receive, downstream calls, and `Wait` each have an explicit release event. A downstream client that ignores context can still make `Wait` hang, so the HTTP path needs finite transport/request deadlines and body closure.

The overload policy is cancellable backpressure. If waiting is unacceptable, use a service-wide concurrency limiter and reject before work with `429` or `503`; rejecting after effects start requires idempotency or an explicit partial-result contract.

### Skill-assisted output, normalized — 10/10

Use a request-scoped fixed pool of eight workers and an unbuffered job channel. Do not create one goroutine per image and do not use a results channel. The owner starts workers in an `errgroup`, cancellation-aware submits jobs, closes the jobs channel, and waits. Workers return the first material error through the group, which cancels sibling calls.

The handler is the only producer and closer. The answer enumerated blocking on job submission, job receive, the downstream call, and `Wait`, with cancellation, channel close, response, timeout, or worker termination as the corresponding release events. Cancellation cannot terminate a downstream call that ignores its context, so the call also needs finite timeouts.

The unbuffered channel makes admitted work and per-request downstream concurrency explicit. It also distinguishes this from aggregate service capacity: if eight is a service-wide limit, use a shared bulkhead and separately bound waiting requests, rejecting overload with `429` or `503` rather than turning blocked handlers into another unbounded queue.

## Scenario 3 — retry amplification and recovery

### Prompt

A Go checkout API has a 900 ms client-visible SLO. It calls Payment, which calls Risk, which calls a bank. Every hop currently retries up to 3 times with exponential backoff. During a bank latency event, request volume and goroutine count surge, p99 exceeds 8 seconds, and recovery is slow. Some payment requests are safe to replay only when the caller supplies a stable idempotency key. Design the end-to-end deadline, retry ownership and budget, backoff/jitter, replay-safety checks, concurrency/load shedding, and recovery behavior. Explain why adding circuit breakers at every hop is or is not sufficient.

### Rubric

Absolute propagated deadline; useful-work admission budget; one retry owner and amplification control; transient/ambiguous classification; capped full jitter and Retry-After; durable idempotency/fingerprint/reconciliation; pre-work dependency bulkhead and shedding; retry capacity protection; gradual recovery without stale backlog; limits of circuit breakers.

### Baseline output, normalized — 10/10

Set one absolute ingress deadline around 850 ms to preserve response margin and propagate it through every hop without resetting it. Allocate measured sub-budgets and start an attempt only when the remaining deadline covers minimum useful timeout, backoff, and upstream response reserve. Every wait must observe cancellation.

Give retry ownership to the bank integration; upper layers call downstream once. Permit at most one classified retry under a global retry budget. Retry only documented transient connection/status failures, use capped exponential full jitter, honor `Retry-After` only inside the remaining budget, and treat a timeout after transmission as ambiguous.

Payment durably binds a caller idempotency key and scope to a canonical request hash, operation state, result, and downstream IDs. Mismatched reuse is rejected. Without bank idempotency or status lookup, do not replay an ambiguous mutation; record it for reconciliation and return an unknown/pending operation.

Bound work before spawn with service-wide dependency concurrency, small cancellable queues, fairness, connection limits, and early `429`/`503` shedding. During recovery, restore traffic and retry capacity gradually with jitter rather than releasing backlog. Breakers may fail fast at the bank boundary but do not bound queues, prevent retry multiplication, or provide replay safety; synchronized breaker states can worsen recovery.

### Skill-assisted output, normalized — 10/10

Set one absolute approximately 850 ms checkout deadline, propagate it unchanged, reserve completion time, and use measured sub-budgets. Before queueing, sleeping, or attempting, require enough remaining time for queue wait, useful attempt, backoff, and response margin.

Remove nested retries: three retries beyond the initial attempt at three hops can produce up to `4^3 = 64` bank calls. Make the bank adapter the sole retry owner, allow at most one retry, and constrain it by both deadline and a global retry-token budget. Classify outcomes, use capped exponential full jitter and bounded `Retry-After`, and treat post-send timeout as ambiguous.

Payment durably binds a stable key to fingerprint, state, result, and ambiguous/reconciliation state; mismatched fingerprint reuse is rejected and the same key flows downstream. Without remote dedupe or reconciliation, return pending/unknown rather than retrying under a new key.

Acquire a bounded bank bulkhead before spawning work or retry state, bound wait duration, shed cheaply, and make retries share the pool while using a separate token budget so they cannot displace all first attempts. Gradually restore admission and retry capacity, jitter probes, and discard expired queued work. Breakers do not establish replay safety, prevent pre-open amplification, bound goroutines/queues, or enforce deadlines; an indiscriminate breaker at every hop adds interacting state machines.
